# Issue #195:委派触发条件从「建议」改成可数硬条件

> 三问:① 可拆 = 否(单一文件 + 一个测试文件,文本改动);② 值得第二视角 = 是(改的是常驻注入的纪律文本,措辞偏差会直接影响每个会话的行为);③ 可并行 = 否。
>
> 分级:**standard**(改动小但影响面大:注入文本对每个会话每一步生效)。

## 背景

用户问「现在会按照任务自动拆解并且派发吗」,实测答案:**不会自动,只是建议**。

证据(2026-11-12,本机):

- 注入的 13 条 bullet 里含「应当/建议/宁可」这类软措辞,**没有任何一条是「必须」**(实测 `/必须|强制/` 在整段文本中零命中)。
- `stall-governor` 的实时配置是 `mode: "shadow"`(`/root/.dsh/storages/stall-governor.json`),即**仅观测、不拦截**。
- 仓库自己的事故记录 `docs/specs/issue-186`(issue #186):「20 个文件的任务全程单线程,首次委派迟到 24.7 分钟/148 次调用」。

现有触发条件是「≥3 个同类独立单元」——不可数、靠模型自我评估,且没有堵住「我先看看再说」这个逃生口。

## 目标

把触发条件改成**可数信号**,让「该不该拆」变成能当场数出来的判断,而不是感觉:

1. 要改 **≥3 个文件** → 必须拆;
2. 要动 **≥2 个包/模块** → 必须拆;
3. 要跑 **≥2 个互不依赖的验证**(如两套测试、两个仓库的检查)→ 必须并行;
4. 明确堵住逃生口:不许用「先读一遍看看」「先摸清情况」当理由跳过拆解——读也要分给子 agent 读。

## 边界

- **只改文本**,不动 governor 档位(保持 `shadow`)、不加拦截规则、不改任何代码逻辑。
- 不改 `ROUTING` 表、不动 `DELEGATION_PRESET_WHITELIST`。
- 不引入「强制编排」(staged + Approve & Run 那一套,属另一量级)。
- zh/en 两份字典**结构必须对称**(既有契约测试守护 bullet 数一致)。

## 验收

1. 新文本含**可数数字信号**(≥3 文件 / ≥2 包 / ≥2 验证),且能用正则断言出来。
2. 新文本含**反逃生口**条款(明确「先看看」不构成跳过理由)。
3. zh/en bullet 数一致(既有契约测试)。
4. 新断言可反向验证:删掉任一条款 → 对应测试变红。
5. `pnpm test` + `pnpm verify` 全绿;`dsh-task-dispatcher` 升版 + CHANGELOG。
